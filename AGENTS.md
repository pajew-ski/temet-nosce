# AGENTS.md

Public GitHub repo, project name **temet-nosce** (means "know thyself" or "know yourself"). Content: an n8n agent that explains itself and its own blueprint through graph retrieval, plus an n8n MCP server that hands the same graph, reads and writes, to any MCP client. The graph describes the repo it lives in, and the path for building such a system from scratch, including this AGENTS.md as the first component.

Target audience: complete beginners to graphs. The goal isn't production readiness, it's that someone comes away thinking in nodes and edges instead of folders and prose.

## Non-Goals

- No vector DB, no embedding step
- No build tool, no framework, no bundler for the website
- No auth (public showcase)
- No manual dark/light toggle. Automatic only, via `prefers-color-scheme`

## Data Model

### Node Schema (`graph/nodes/<id>.md`)

```yaml
---
id: <string, == filename without .md>
type: Project | Concept | Component | Step | Limitation
edges:
  - rel: <string>
    target: <id of another node>
---
<free text body, currently notes only>
```

Edges are directed, defined once. No back-edges. The index is globally visible to the agent, so direction only matters for maintenance, not for retrieval.

### Index Schema (`graph/index.md`)

```markdown
## <id>
type: <type>
notes: <comma separated>
edges: <rel> -> <target>, <rel> -> <target>
path: graph/nodes/<id>.md
```

No longer hand-maintained. Generated by `scripts/sync-graph.mjs` from the node frontmatters. One block per node, flat text, fits entirely into the system prompt of the n8n AI Agent node.

## Sync Script (`scripts/sync-graph.mjs`)

- Bun, no external dependencies. The frontmatter schema is constrained enough for a small hand-written parser, no need for `js-yaml` or similar
- Reads all `graph/nodes/*.md`, extracts `id`, `type`, `notes`, `edges`
- Writes `graph/index.md` per the index schema
- Writes `docs/graph-data.json` as `{nodes: [{id, type, notes}], edges: [{source, target, rel}]}`
- Rewrites the index inside the system prompts of both chat workflow JSONs (`workflow-variant-a/b`), replacing only what follows the `THE INDEX` marker, so the workflows never drift from the nodes either. `workflow-mcp-server.json` embeds no index copy; its `read_index` tool fetches `graph/index.md` live and needs no sync
- Validates along the way: every edge must point to an existing `id`, otherwise it errors with file name and line, non-zero exit code
- Invocation: `bun scripts/sync-graph.mjs`, no flags needed

## GitHub Action (`.github/workflows/sync-graph.yml`)

- Trigger: push to `graph/nodes/**`
- Steps: checkout, install Bun via `oven-sh/setup-bun` (GitHub-hosted runners don't ship Bun preinstalled the way they do Node, this is the one third-party action needed), run `bun scripts/sync-graph.mjs`, commit and push if `graph/index.md`, `docs/graph-data.json`, or an `n8n/*.json` workflow changed (plain git CLI beyond that)
- Purpose: editing a node file is enough, the index and the visualization catch up automatically. A forgotten local sync gets caught by the action.
- The MCP server's write tools commit into `graph/nodes/**` through the Contents API, and API commits fire push events, so the same action is what makes MCP writes reindex automatically.

## Design System

Beauty is a first-class requirement, not a finishing touch. The design follows albedo: achromatic color, and every spacing, sizing, and typography decision derived from a single base, 2.

### Tokens (albedo)

The stylesheet begins with the albedo token block, from `/* albedo: Anfang */` to `/* albedo: Ende */`, markers included. The block is identical, byte for byte, in all four repos of the family (temet-nosce, open-desensitizer, open-entrainer, open-helix); a change to it is a change to all four. Its source lives in a private repository, so the tables below are the reference here.

Tones, `oklch(L 0 0)`:

| Token | Light | Dark |
|---|---|---|
| `--bg` | 98% | 15% |
| `--surface` | 94% | 23% |
| `--border` | 85% | 32% |
| `--text` | 15% | 95% |
| `--text-muted` | 40% | 70% |

Geometry:

| Token | Value | Rule |
|---|---|---|
| `--step-2` … `--step-7` | 4, 8, 16, 32, 64, 128 px | 2ⁿ px |
| `--radius-sm`, `--radius-md`, `--radius-lg` | `--step-2`, `--step-3`, `--step-4` (4, 8, 16 px) | |
| `--type-sm` | 0.875rem | 14px, 1 − 2⁻³, the legibility floor |
| `--type-0` … `--type-4` | 1, 1.414, 2, 2.828, 4 rem | 2^(k/2) rem |
| `--leading` | 1.414 | √2 |
| shell (outside the block) | 1024px max width | 2¹⁰ |
| text column (outside the block) | 32rem max width | 2⁵ rem |

- Color is achromatic. Chroma 0 cannot tint; light and dark share one scale and flip with `prefers-color-scheme`. `color-scheme: light dark` on the root so form controls follow. There is no switch, neither for the scheme nor for the language.
- Hue exists only as a data channel: `oklch(var(--hue-l) var(--hue-c) H)`, with `--hue-l` 45% light and 75% dark, `--hue-c` 0.11, and the angle H free. Hue never carries meaning alone; a second mark (shape, position, label) always goes with it.
- Geometry derives from 2, the same growth as the Krystal Flower. A size the tokens do not cover takes the nearest power of two, a font size the nearest √2 step, never below 0.875rem. Exceptions: the 1px hairline, the 44px tap target, radii of half the element height (circles and pills stay round), and values that belong to a foreign system.

**Layout**: graph canvas and detail side panel split at √2:1, the half step of the base-2 scale, not 50/50

```css
.layout { grid-template-columns: minmax(0, 1.414fr) minmax(0, 1fr); }
```

`minmax(0, …)` rather than a bare `fr`: Cytoscape gives its inner wrapper an explicit pixel size on every resize, and a bare `fr` track treats that as a content minimum, so after an orientation flip the stale wrapper size would lock the canvas at its old width.

The graph canvas keeps the √2 ratio as well, but derived from the viewport (`clamp(340px, 71vh, 700px)` in landscape, a `100vw`-derived height in portrait) rather than declared with `aspect-ratio: 1.414 / 1`: WebKit mis-sizes an empty grid item that carries an `aspect-ratio` and collapses the canvas to nothing on phones and tablets in portrait.

No CSS framework. `docs/style.css` is hand-written and semantic (`.shell`, `.hero`, `.layout`, `.panel`), with layout coming straight from grid and flex. Nothing is generated: no utility classes, no build step, no palette that would reintroduce a hue. All color comes from the custom properties above.

## Website (`docs/`)

Stack, everything via CDN, no npm, no bundler:

- **Cytoscape.js** (CDN script) for the graph visualization, node/edge colors pulled from the design tokens instead of Cytoscape's defaults. Layout is `preset`, with the positions computed in `graph.js`: the project at the center, the build steps on an inner ring in sequence order, components and concepts on outer rings, each pulled toward the neighbours it connects to. A force layout like `cose` scatters a graph this small differently on every load; a deterministic radial one shows the structure the graph actually has
- **`@n8n/chat`** (CDN module) for the chat widget, themed through its own custom properties
- Everything else is hand-written: one stylesheet and three small ES modules, no framework, no utility-class library (see Design System)

`index.html`, single page, three sections:

1. Short explanation (max. 150 words): what a knowledge graph is, index as retriever instead of similarity function, distinction from vector RAG. Where the copy names the number of node files, that number is written into a `#node-count` span and overwritten from `graph-data.json` at load, spelled out in words: a hand-counted number in prose is a fact that silently goes stale the first time a node is added
2. Graph visualization: fetch `graph-data.json`, render with Cytoscape in a √2 rectangle, clicking a node shows its notes and edges in a side panel sized at the √2:1 split
3. n8n chat widget: `@n8n/chat`, fully wired at build time, not a placeholder

   ```html
   <link href="https://cdn.jsdelivr.net/npm/@n8n/chat/dist/style.css" rel="stylesheet" />
   <script type="module">
     import { createChat } from 'https://cdn.jsdelivr.net/npm/@n8n/chat/dist/chat.bundle.es.js';
     createChat({ webhookUrl: 'WEBHOOK_URL' });
   </script>
   ```

   `WEBHOOK_URL` as a single constant at the top of `chat.js`, filled in after importing one of the two n8n workflow variants. Theme the widget by overriding its CSS custom properties with the site's design tokens, for example:

   ```css
   :root {
     --chat--color-primary: var(--text);
     --chat--color-secondary: var(--text-muted);
     --chat--color-white: var(--bg);
     --chat--color-light: var(--surface);
     --chat--color-dark: var(--text);
     --chat--spacing: var(--step-4);
     --chat--border-radius: var(--radius-sm);
     --chat--font-family: inherit;
   }
   ```

   Variable names have shifted across `@n8n/chat` versions, confirm the exact names against the installed version before wiring this up. Either way, the effect is the same: the widget loses its default pink/teal accent and inherits the neutral palette.

### Dark / Light Mode

Automatic only, no toggle. Same neutral tokens from the Design System, swapped via `prefers-color-scheme`.

- The `:root` custom properties (`--bg`, `--surface`, `--text`, ...) switch through the `@media (prefers-color-scheme: dark)` block, which covers everything styled in CSS: the page itself, and the chat widget through the `--chat--*` properties that reference these tokens
- Cytoscape draws on a canvas, so it does not pick up `:root` changes on its own and has to read the current theme in JS. `docs/theme.js` is one small module for that, no dependency:

  ```js
  export function getTheme() {
    return window.matchMedia('(prefers-color-scheme: dark)').matches ? 'dark' : 'light';
  }
  export function onThemeChange(callback) {
    window.matchMedia('(prefers-color-scheme: dark)').addEventListener('change', e => {
      callback(e.matches ? 'dark' : 'light');
    });
  }
  ```

  `graph.js` uses it to pick Cytoscape's style values on init and re-style on change. The chat widget needs no JS for this: its `--chat--*` properties are declared in `style.css` against the site tokens, so it flips with the page and `chat.js` stays out of theming entirely.

`graph.js` and `chat.js` both stay thin: fetch/init, read theme via `theme.js`, one or two event handlers. No state management, no framework.

## n8n Workflows (`n8n/`)

Three complete, independently runnable workflows: two chat agent variants (same agent, different retrieval tool, shows that the pattern isn't tied to a specific tool) and one MCP server that exposes the graph to external clients.

**Variant A — `workflow-variant-a-http-tool.json`**
- Chat Trigger node (public, provides the webhook URL for the website widget)
- AI Agent node, system prompt = full content of `graph/index.md`
- Tool: HTTP Request node, GET against `https://api.github.com/repos/<owner>/<repo>/contents/<path>`, header `Accept: application/vnd.github.raw`, one parameter `path`
- Credential: GitHub PAT with no scopes, only needed for a higher rate limit

**Variant B — `workflow-variant-b-github-node.json`**
- same Chat Trigger + AI Agent node
- Tool: native n8n GitHub node, resource `File`, operation `Get`, parameters `Owner`/`Repository`/`File Path` taken from the `path` field of an index block
- Credential: GitHub App or OAuth2 credential through n8n's own node type

Tool description is identical in both cases: the path parameter comes from the `path` field of an index block.

**MCP server — `workflow-mcp-server.json`**
- MCP Server Trigger (path `temet-nosce-graph`), no model node inside: the connecting MCP client brings its own model, which reads the index and drives the multi-hop loop itself
- Read tools as plain HTTP Request tool nodes, unauthenticated like variant A: `read_index` (GET `graph/index.md` raw, the entry point), `get_node` (GET one node file raw, parameter `path`, one call per hop)
- `search_nodes`: GET `https://api.github.com/search/code`, query = model's terms plus fixed `repo:` and `path:graph/nodes` qualifiers, `Accept: application/vnd.github.text-match+json`. GitHub requires auth for code search, so this node uses the GitHub credential
- Write tools as native GitHub nodes like variant B, because the native node hides the base64/sha bookkeeping that Contents API writes need: `create_node` (File Create), `update_node` (File Edit), `delete_node` (File Delete). File path is locked to `graph/nodes/<id>.md` with only `<id>` model-filled, so the tools cannot write outside the graph. One commit to `main` each, commit message `mcp: <verb> graph/nodes/<id>.md`
- Reindexing after writes is automatic: the commit trips `sync-graph.yml` (see GitHub Action section)
- Credential: one GitHub credential (fine-grained PAT, contents read/write on this repo only) shared by `search_nodes` and the three write tools; `read_index`/`get_node` run unauthenticated

`n8n/README.md`: setup steps for all three workflows, credential setup, note that the webhook URL needs to be entered in `docs/chat.js` after import, short comparison of when to use which chat variant (A transfers to other APIs, B needs less configuration for a GitHub-only use case), and how to connect an MCP client to the server URL.
